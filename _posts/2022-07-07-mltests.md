Cross validation tells you how good a model is on average. It doesn't tell you how it behaves in the situations your users care about. For that, you need tests, the same way software has tests. Here's the story of how I learned that.

## The story

A while back, I was on a small team building a text classifier. Its output showed up in an interface our clients used.

We evaluated it with plain cross validation (stratified, since the data was very imbalanced). That's the standard bible, what could go wrong, right? The scores were good, and I felt confident.

Then the complaints started. Every now and then, a client would see texts misclassified that were nearly identical to ones we had explicitly added to the training set.

Missing a case that looks like nothing you've ever seen is at least a forgivable error. How would you know what you don't know, right? But missing something almost identical to what you've trained on is serious. Over time, it erodes the client's trust in every result.

We had to find a way to QA the classifier. That's when it clicked: a single test set, even cross validation, would never tell us how the model behaved in production. We needed to know exactly how it handled specific situations, and decide from that whether it was ready to release.

Does that ring a bell?

## An ML model is software

In regular software development, you write code that does certain tasks in certain ways. With ML, you kind of write code that writes the code. You save a lot of time working out the logic yourself, because the machine learns it from examples.

Once the model has seen the data, its logic is fully fixed. It's just a deterministic piece of software.

But not everything the machine learns is what you intended. Push it hard enough and a model will learn a bunch of random bullshit. So you need a way to check that the code the machine wrote behaves the way you want before you ship it. In other words, you need tests.

## Testing a model like you test software

In software, you want your code to behave in a known way. So you think about where it might break, and you write tests for those cases. Once it passes them, you trust it more in the real world, because you've already seen how it handles those scenarios.

That's what I was missing. All I had were cross validation scores. Nothing wrong with those: they're the right tool when you compare algorithms head to head, like in research. But testing as part of shipping software has a different job. It tells you exactly what your code does, and how.

## Building test cases for ML models

There's no one-size-fits-all way to test models, because there are so many ways to model. In some domains you can generate synthetic samples that simulate specific scenarios. Finance does this a lot.

In other domains, synthetic data is hard to come by, so you have to dig into your real data to build scenario-based test sets. Here's one way.

Some algorithms work by grouping similar samples together. You can use those groups to build test sets from real data: pick a few samples from each group to stand for that kind of case. Then test any model against them and see how it does on each kind of case. A compact test set like this also gives you leads when a model keeps failing the same case.

Kernel methods and other similarity-based methods are good for this. So are neural networks: you can think of one as a linear model sitting on top of a learned kernel. Take the output of the layers before the final linear layer, and you'll usually find that similar samples sit close to each other.

Just as different kinds of software need different kinds of tests, different ML algorithms need different ways of building test sets. Testing a classifier is not the same as testing a regression model.
